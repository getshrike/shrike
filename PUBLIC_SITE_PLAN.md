# Public Website and Consumer Docs Implementation Plan

## 1. Objective

Add a public landing-site scaffold and a complete first version of consumer documentation to the existing Shrike repository. Keep the site and documentation source in separate directories and deployable independently. Do not alter Shrike's CLI behavior, Rust engine, npm package contents, release flow, or existing contributor documentation.

This is a plan for repository work. It does not authorize publishing a site or connecting a production domain.

## 2. Decisions and repository layout

Use this layout:

```text
apps/
  site/                  # Next.js + shadcn setup only
  docs/                  # Mintlify config and public MDX pages
docs/                    # existing engineering/contributor documentation; preserve
PUBLIC_SITE_PLAN.md      # this plan
```

Use `apps/site` for the landing-site scaffold and `apps/docs` for Mintlify. This follows established monorepo naming: [next-forge](https://github.com/vercel/next-forge) uses `apps/web` for its marketing site and `apps/docs` for Mintlify, and [Prisma's web repository](https://github.com/prisma/web/blob/main/ARCHITECTURE.md) uses `apps/site` and `apps/docs` for separate web zones. Shrike has no existing web product app, so `site` clearly identifies the marketing site without suggesting that it is a user-facing application.

The root `docs/` already serves contributors and coding agents. Do not move, rename, replace, or convert those files into consumer docs. Mintlify must use `/apps/docs` as its configured content directory.

## 3. Landing site: scaffold only

### Required result

Create a working Next.js application in `apps/site` and initialize shadcn/ui using the latest stable release available when implementation begins. The generated starter page is the stopping point for this phase.

### Steps

1. Recheck the current npm `latest` tags immediately before scaffolding. As checked on 2026-11-24, they resolve to Next.js and `create-next-app` `16.4.6`, shadcn CLI `4.23.0`, and Mintlify CLI (`mint`) `4.3.85`. Treat these as dated references, not pins; install stable `latest`, never `canary`, `preview`, `beta`, or `rc`, then record the exact resolved versions in lock/config where applicable. References: [Next.js npm package](https://www.npmjs.com/package/next), [create-next-app npm package](https://www.npmjs.com/package/create-next-app), [shadcn npm package](https://www.npmjs.com/package/shadcn).
2. Before generating the app, add `apps/*` to `pnpm-workspace.yaml`. The current workspace includes only `packages/*` and `packages/platform/*`; adding the app glob first ensures the generated package is recognized as a workspace package during install. `apps/docs` will have no `package.json`, so it will remain content rather than a pnpm package. See [pnpm workspace docs](https://pnpm.io/workspaces).
3. From the repository root, run `pnpm create next-app@latest apps/site --yes`. The current recommended defaults provide TypeScript, ESLint, Tailwind CSS, App Router, Turbopack, and the `@/*` import alias. If the generator uses saved preferences that differ, rerun interactively and choose those exact options. This repository's Node requirement (`>=22`) satisfies Next.js's documented minimum (`20.9`). See the [Next.js installation guide](https://nextjs.org/docs/app/getting-started/installation) and [shadcn Next.js instructions](https://ui.shadcn.com/docs/installation/next).
4. Set the generated package name to `@shrike/site` while preserving the generator's dependency versions and scripts. If generation did not update the root lockfile as part of workspace install, run the repository-pinned `pnpm install` from the root. Do not create a nested lockfile.
5. From `apps/site`, run `pnpm dlx shadcn@latest init`. This is the official existing-project setup path; do not use shadcn's alternative command that scaffolds a new Next.js app because Next.js has already created it. Use the CLI's standard setup and keep generated component code in this app; do not create a shared component package or a design-system workspace. Initialization should create `components.json` and any configuration/CSS files it requires. See [shadcn's Next.js installation guide](https://ui.shadcn.com/docs/installation/next).
5. Keep the generated Next.js starter route and styles as generated. Do not redesign or replace the homepage, edit its content, add Shrike branding, write marketing copy, add a navigation/header/footer, add custom sections or assets, install individual shadcn components, or configure analytics/SEO/deployment in this phase. Do not make a hand-written `app/page.tsx` change to demonstrate shadcn; initialization is the shadcn setup required here.
6. Keep app scripts local to `apps/site` (`dev`, `build`, `lint`, and `typecheck`). Use scripts generated by the current Next.js template where present and add only a `typecheck` script if absent. Root CLI build, test, bundle, package, and release scripts must not depend on the site.

### Landing-site acceptance

- A clean checkout can install the workspace, run the site's development server, and create a production build.
- Next.js resolves to the latest stable release checked at implementation time; shadcn is initialized with its latest stable CLI and a valid `components.json`.
- The Next.js-generated starter page remains intact apart from any direct file changes the shadcn initializer requires. No landing-page design/content work is included.

## 4. Mintlify consumer documentation

### Setup and structure

1. Confirm Node.js is at least `20.17.0` for the current Mintlify CLI setup guidance; Shrike requires Node `>=22`, so no root runtime change is needed. Install/update the CLI with `npm install --global mint@latest` (do not install the legacy `mintlify` package). As checked on 2026-11-24, `mint@latest` is `4.3.85`; recheck before use. See [Mintlify CLI setup guidance](https://www.mintlify.com/library/mintlify-agent-skill).
2. Create `apps/docs/docs.json` and the public MDX files directly; do not run a starter generator that would add unrelated placeholder pages. Configure Mintlify's GitHub integration to read the subdirectory `/apps/docs`. Mintlify supports a docs config in a monorepo subdirectory; the existing root `docs/` remains independent. See [Mintlify monorepo setup](https://www.mintlify.com/docs/deploy/monorepo.md).
3. Write all public pages as `.mdx`. Use lowercase kebab-case page filenames and organize them into `getting-started/`, `guides/`, and `reference/` directories. Put images/downloadable public assets under `apps/docs/images/` only when required. Do not copy internal-only contributor material into this tree.
4. Use one Mintlify `navigation.groups` sidebar, ordered for a new user: Get started, Core workflow, Integrations, Reference, Troubleshooting. List pages in reading order and use extensionless paths in `docs.json`.
5. Give each page YAML frontmatter with a human-readable `title` and useful `description`. Keep headings task- or question-focused. Use Mintlify built-in MDX elements only where they help (for example, `<Note>` for a prerequisite, `<Warning>` for a mutation boundary, and `<Tabs>` only for meaningful platform alternatives); avoid decorative component use.
6. Use the content pattern established by Mintlify examples: task-oriented navigation, short page metadata, procedures with numbered steps, copyable code, expected outcomes, and links to the next task. Built-in components are available in MDX without imports. See [Mintlify content setup guidance](https://www.mintlify.com/library/how-to-turn-markdown-files-into-a-docs-website) and the [official docs](https://www.mintlify.com/docs).

### Source-of-truth rules

Before authoring, read these repository sources and use them to resolve page facts:

- Product purpose, installation, quick start, command descriptions, limitations, and published behavior: root `README.md` and `docs/features.md`.
- Current command names, flags, examples, JSON support, mutation semantics, and exit codes: CLI help and implementation under `packages/cli/src/`.
- Config fields and defaults: `schemas/config.schema.json` plus the TypeScript config loader.
- GitHub Action modes, inputs, permissions, and fork behavior: `packages/action/action.yml`, action source, and existing integration docs.
- Hook events/budgets and MCP tools/limits: `docs/features.md` and `packages/agent/` source.
- Distribution/platform support and runtime requirements: `docs/release.md`, platform package metadata, and `packages/cli/package.json`.
- Verification, receipt, and recovery behavior: `packages/verifier/`, `packages/receipts/`, schemas, and `docs/features.md`.

When sources conflict, current executable behavior and schemas win. Do not invent command flags, config options, supported platforms, event coverage, guarantees, or behavior. Keep performance statements tied to the recorded benchmark method/results and do not describe machine-specific numbers as universal guarantees. Code examples must be copied from or checked against the actual CLI/action/config interfaces.

Create these pages in this order. The table is the initial complete v1 content set; add a page only if required to keep one page focused on one task.

### Mintlify docs acceptance

- `docs.json` parses and the sidebar includes every intended page exactly once in a useful order.
- Every page renders in the local Mintlify preview, has title/description frontmatter, and has no broken local links or missing assets.
- All shell/YAML/JSON examples agree with current Shrike behavior, schemas, package metadata, and declared GitHub Action permissions.
- The docs explain mutating behavior and limitations before users run the relevant command; read-only and mutating operations are not conflated.

## 5. Repository integration, CI, and performance boundaries

- Register `apps/site` in the existing pnpm workspace; keep Mintlify content outside pnpm package management. Commit the lockfile update caused by the site's workspace dependencies.
- Add a focused website/docs workflow. Site changes should run site typecheck, lint, and production build. Docs changes should run `mint validate` and `mint broken-links` from `apps/docs`. Install a stable Mintlify CLI version in CI and pin the exact version selected during implementation so the docs gate does not change underneath the lockfile. Include workspace/lockfile changes in relevant workflow triggers. See [Mintlify's documented CLI checks](https://www.mintlify.com/library/mintlify-agent-skill).
- Add path-ignore rules to the current Shrike CI trigger for site-only and consumer-docs-only changes, while preserving the full existing CI when a pull request mixes site/docs changes with engine/CLI/schema/fixture changes. The focused workflow must still run for site/docs edits.
- Do not add website assets or dependencies to CLI/action bundler inputs, npm file allowlists, platform packages, or release jobs. Verify the packed CLI still contains only its existing runtime files.
- Runtime performance of the Shrike CLI should not change because the new site/docs do not execute in the CLI. The workspace install and root lockfile become larger; focused CI avoids running the full engine matrix for isolated site/docs-only edits. Keep build/deploy tasks independent.

## 6. Ordered execution checklist

1. Confirm the current branch and preserve any existing worktree changes. Read the source-of-truth files listed above before editing docs.
2. Scaffold `apps/site`, confirm latest stable package tags, initialize shadcn, register the app in pnpm, and leave the generated homepage untouched.
3. Add `apps/docs/docs.json`, set the intended navigation, then author MDX pages in the inventory order, verifying facts against code/schema during writing.
4. Add focused site/docs CI and adjust existing CI triggers so mixed changes still run Shrike gates.
5. Run `pnpm install --frozen-lockfile`, the site typecheck/lint/build scripts, then from `apps/docs` run `mint validate`, `mint broken-links`, and `mint dev`. Manually follow the sidebar and review command examples. Run existing repository documentation/link checks and package check to confirm the new paths do not break existing gates or alter CLI packaging. Mintlify's documented workflow is to preview with `mint dev`, validate with `mint validate`, and check internal links with `mint broken-links`. See [Mintlify setup and checks](https://www.mintlify.com/library/publish-open-source-local-docs-on-mintlify).
6. Review the final diff to ensure the landing route is still the generated scaffold, the existing root `docs/` is unchanged, and there are no Rust, CLI, protocol, schema, release, or runtime changes.

## 7. Assumptions and explicit non-goals

- The landing deliverable is **only** a Next.js scaffold with shadcn initialized. No custom landing-page changes are permitted in this phase, including replacing the generated homepage with Shrike copy/design or adding shadcn components.
- The consumer docs are public, English-only, and based on current product behavior. No new Shrike features or public API changes are part of this work.
- Hosting account, production domain, deployment provider, analytics, and production publication are undecided and out of scope. Mintlify and Next.js should run and validate locally; the repository layout should be deployable later.
- Keep README edits out of this phase so the landing-page setup remains strictly scaffold-only; link the published docs from the README in a later publishing/content pass.
